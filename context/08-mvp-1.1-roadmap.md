# Chronoflow — Plan de ejecución del MVP 1.1

Última actualización: **2026-08-22** (MVP-113 merged a main).

## Propósito

Este documento divide el MVP 1.1 en tareas que pueden ejecutarse en sesiones independientes de OpenCode.

Cada tarea tiene un alcance acotado, un branch sugerido y criterios de aceptación propios. `06-current-status.md` continúa siendo la fuente de verdad para saber cuál tarea está activa y cuáles ya terminaron.

## Política de versionado del contexto

La carpeta `context/**` está excluida por el `.gitignore` vigente. Estos documentos sirven como contexto operativo local y permanecen disponibles al cambiar de sesión o branch, pero no forman parte de commits ni Pull Requests.

No modificar esta política ni forzar archivos de `context/` al índice sin una decisión explícita del usuario. Los branches definidos en este documento contienen los cambios de aplicación y sus tests; el progreso se actualiza localmente en `06-current-status.md` y en este archivo.

## Objetivo

Mejorar la experiencia del MVP desplegado sin introducir todavía backend, autenticación, sincronización, chat IA ni notificaciones.

## Decisiones vigentes

- La duración predeterminada de cada slide es `5000 ms`.
- Las preferencias del MVP 1.1 se guardan localmente y no pertenecen a un usuario autenticado.
- La duración de slides es una preferencia global de Presentation View, no una propiedad de cada timer.
- Ocultar segundos cambia únicamente la presentación, no los cálculos internos.
- Cada tarea se desarrolla en un branch independiente y se integra a `main` mediante Pull Request.
- `Update`/`Edit` solo entra al alcance si se cumple la condición definida en `MVP-117`.
- Supabase, autenticación, IA y notificaciones permanecen fuera del MVP 1.1.

## Alcance comprometido

- mejorar estados vacíos y de error;
- duplicar timers;
- mostrar u ocultar segundos;
- configurar globalmente la duración de slides;
- personalización visual básica;
- reordenar timers;
- accesibilidad y hardening;
- regresión, documentación y release.

`MVP-117` se ejecuta después de `MVP-116` únicamente si su gate de entrada se aprueba.

## Flujo para cada sesión

1. Leer `README.md`, `06-current-status.md` y este documento.
2. Confirmar que la tarea anterior requerida está completada.
3. Actualizar `main` y crear el branch indicado para la tarea.
4. Implementar únicamente el alcance del ticket activo.
5. Agregar o actualizar tests automatizados.
6. Ejecutar tests, lint y build.
7. Realizar el checklist manual específico de la tarea.
8. Actualizar localmente `06-current-status.md` y este documento.
9. Crear un Pull Request hacia `main`.
10. Iniciar la tarea siguiente desde un `main` actualizado después del merge.

Comandos base:

```bash
git switch main
git pull
git switch -c <branch-de-la-tarea>
```

## Definition of Done general

Una tarea solo puede marcarse completada cuando:

- cumple todos sus criterios de aceptación;
- incluye tests para el comportamiento nuevo o modificado;
- no rompe los flujos existentes;
- pasan test, lint y build;
- se verificó manualmente en desktop y mobile cuando afecta UI;
- se actualizaron localmente los documentos de `context/` afectados;
- el Pull Request fue integrado a `main`.

## Pull Request mínimo

Cada Pull Request debe indicar:

- ticket y objetivo;
- alcance implementado;
- elementos explícitamente fuera de alcance;
- tests agregados o actualizados;
- resultado de test, lint y build;
- pruebas manuales realizadas;
- cambios de persistencia o migración, si existen;
- decisiones o seguimiento local que se actualizaron en `context/`.
